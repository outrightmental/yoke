# Design overview

`yoke` is an orchestration loop for repositories where Claude (Anthropic, via the `claude` CLI / Claude Code) is the implementation worker. Its job is not to replace project judgment; its job is to remove the repetitive coordination work between intent, implementation, review, fixup, description, and merge.

## Product thesis

Agentic coding gets interesting when a repository can keep moving after a human has written the backlog. A single prompt to Claude can produce a patch, but a useful software project needs an operating system:

- choose the next safe item,
- respect dependencies,
- limit parallel work,
- run the implementation locally and open the resulting PR,
- gate on CI before reviewing,
- run a self-review pass (twice, requiring two consecutive clean passes),
- detect and resolve conflicts,
- detect and fix failing checks,
- produce a reviewable final description,
- merge only when the loop is complete.

`yoke` makes that operating system explicit and inspectable.

## Design goals

1. **GitHub-native control plane**: Issues, pull requests, review threads, checks, and merge state remain the primary coordination surface.
2. **Small local brain**: The orchestrator persists only session metadata needed to avoid duplicate work and understand the current phase of each item.
3. **Dependency-aware backlog flow**: Issue ordering starts with bugs first, then milestone, then age, filtered by plain-English dependency phrases and GitHub parent/child relationships.
4. **Bounded autonomy**: `MAX_CONCURRENCY` prevents uncontrolled fan-out. A planning mutex prevents double-booking across concurrent engine threads.
5. **Review-first completion**: Work is not done when a PR appears; it must pass two consecutive clean self-review passes (or a human review in Project SDLC) before merging.
6. **Clean final merge artifact**: The final PR body and squash commit body are generated by Claude from the branch context and preserve closing references.
7. **Human escape hatch**: The `manual` label opts any issue or PR out of automated work at any time.

## Non-goals

- Replacing GitHub project management.
- Replacing human product direction.
- Inventing custom merge semantics outside GitHub's own controls.
- Maintaining a central server. `yoke` is designed as a local or scheduled process that can be stopped and restarted.
- Inventing a custom workflow language. It intentionally leans on issue text, PR metadata, GitHub APIs, authenticated `git`, and `claude`.

`yoke` still treats GitHub as the merge authority. Its default path is a normal squash merge through the GitHub API after the review/fix loop is clean. If branch protection blocks that API merge, `yoke` surfaces the GitHub error instead of attempting a CLI administrator-bypass retry.

## Architecture

```text
                ┌──────────────────────────────┐
                │          GitHub repo          │
                │ issues · PRs · reviews · CI   │
                └──────────────┬───────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────┐
│                             yoke                             │
│                                                              │
│  N engine loops (up to MAX_CONCURRENCY)                      │
│  ─────────────────────────────────────                       │
│  load snapshot  →  reconcile sessions  →  build plan         │
│        │  (serialised via PlanningMutex)       │             │
│        ▼                    ▼                 ▼              │
│  GitHubClient       FileSessionStore      orchestrator       │
│        │                    │                 │              │
│        └────────────────────┴─────────┬───────┘              │
│                                       ▼                      │
│                               execute actions                │
│                        (one action per engine per cycle)     │
└───────────────────────────────────────┬──────────────────────┘
                                        │
                                        ▼
                                 ClaudeAgentClient
                          (runs `claude` CLI in a checkout,
                           implements / reviews / fixes,
                           commits + pushes the branch)
```

### Core modules

- `src/index.ts` parses configuration, starts the Dashboard, launches N concurrent engine loops, handles graceful shutdown (Escape key), and prints operator-friendly status.
- `src/orchestrator.ts` contains the pure planning rules: dependency parsing, issue eligibility, PR phase selection, and closing-reference logic. Stateless and deterministic.
- `src/actions.ts` translates planned actions into Claude-agent invocations and the corresponding GitHub API calls (open PR, post review comment, update body, squash-merge).
- `src/claude-agent.ts` is the local Claude coding-agent client. It clones / updates a checkout, runs the `claude` CLI with structured prompts, parses sentinel-marked output for structured payloads, and commits / pushes results.
- `src/github.ts` wraps the GitHub REST and GraphQL surface used by the loop (issues, PRs, reviews, review threads, status checks, workflow approvals, project boards, merges).
- `src/reconcile.ts` marks any leftover `in_progress` sessions as `failed` at the start of every iteration — every Claude action runs synchronously, so an active session can only be a crashed-process carcass.
- `src/session-store.ts` persists session state in a local JSON file. Tracks PR comments and comment history. Auto-prunes old sessions (retains the 200 most recent).
- `src/dashboard-server.ts` serves the real-time **Dashboard** at `http://localhost:3000`. Includes the Issue → PR Lifecycle pane, live orchestrator logs, and a GitHub activity feed.
- `src/dashboard-utils.ts` provides event-emission helpers used by `index.ts` to push orchestrator state to Dashboard clients over WebSocket.
- `src/event-emitter.ts` is the global event system (23 event types) used for Dashboard communication.

## Data model

The orchestrator works from a `RepositorySnapshot`:

- open issues (with type, labels, milestone, project status, parent number),
- open pull requests (with conflict / check / review-state hints, draft flag, labels),
- locally persisted agent sessions.

An `AgentSession` records the phase, status, linked issue or PR, timestamps, and small phase-specific result values such as the head SHA observed after a fix push. This is enough to answer questions like:

- Did Claude already implement this issue?
- Did the latest self-review push changes or was it clean?
- Was the penultimate self-review also clean? (Two clean passes → squash merge.)
- Was a final description already generated?

## Planning model

Planning is deterministic:

1. Sort open issues and PRs by creation time.
2. Build a blocked-issue index from `blocked by`, `depends on`, `blocks`, and GitHub parent/child relationships.
3. Plan PR work first — open PRs already consume repository attention and should be shepherded to completion before new issues are started.
4. For each open PR, determine the next action based on session history, conflict state, CI state, and the two-clean-review gate.
5. Count only PRs that are actively being worked (have a planned action or an active session); PRs parked awaiting human review do not consume concurrency capacity.
6. Use remaining capacity for the highest-priority eligible unblocked issues.

This keeps the system conservative: existing work is shepherded before new work starts, and parked PRs do not starve issue capacity.

## Action model

The six orchestrator action types each record a session in the local store. The session phase name matches the action name except for `start-implementation`, which is stored as `implementation`:

| Action | Description |
| --- | --- |
| `start-implementation` (session: `implementation`) | Claude implements the issue in a local checkout and Yoke opens a draft PR. In project mode, the issue moves to "In Progress". |
| `self-review` | Claude reviews the PR diff on the current head, optionally addresses human PR comments, and either pushes fixes or confirms clean. Yoke posts a summary comment. |
| `address-failing-checks` | Yoke fetches failing CI log excerpts; Claude reads them and pushes a fix. Stuck pending checks (> 10 min) are cancelled first. |
| `resolve-conflicts` | Claude rebases the PR branch on the base branch and resolves any merge conflicts. |
| `squash-merge` | Claude generates a final PR body from the branch commits and diff. Yoke updates the PR body, promotes the draft to ready-for-review, and squash-merges. |
| `request-review` | (Project SDLC only) Yoke marks the PR ready-for-review, requests human review, and moves the issue to "In Review" on the project board. |

Each action is idempotence-aware through session state. A later iteration can observe what changed (new head SHA, clean review flag) and move to the next phase instead of repeating the same work.

The squash-merge action subsumes what might otherwise be a separate "write-final-description" step: it generates the description and merges atomically so there is no window where the PR body is updated but the branch is not yet merged.

## Safety and operator control

- Use `--dry-run --once` to inspect the plan without mutating GitHub or running Claude.
- Keep `MAX_CONCURRENCY` low until the repository's issue quality and CI signal are trustworthy.
- Use branch protection and required checks as the final safety net.
- Keep issues small enough for agentic implementation and review.
- Use explicit dependency phrases when order matters.
- Apply the `manual` label to pause automated work on any issue or PR at any time.
- Press **Escape** while the loop is running for a graceful shutdown (finishes in-flight actions before exiting).

## Why the two-clean-review gate matters

A single clean self-review pass is necessary but not sufficient: Claude might fix something superficial on the first pass but miss a structural issue visible only after the fix is committed. Requiring two consecutive clean passes — with a CI gate between any code-changing pass — gives the agent a chance to find its own regressions before merging.

## Why the final-description step matters

Agent-generated PRs often start with sparse or placeholder descriptions. Before merge, `yoke` asks the local `claude` CLI to read the commits and diff on a checkout of the PR branch and write a description from that context. The result becomes both the final PR body and the squash commit body. Closing references are preserved or appended so GitHub issue automation still works.

That turns every merged unit into a useful historical artifact instead of a trail of placeholder text.
